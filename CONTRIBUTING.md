# Contributing to Polaris

Thanks for looking at the code. This page covers what you need to make a change and get it merged: how the tests are laid out, how the dashboard is styled, and how a visual change is checked. The product rules an agent must follow while editing this repo are in `CLAUDE.md`, and they apply to people too.

## Getting set up

Node 24 or newer. The server has no build step.

```sh
git clone https://github.com/owenpkent/polaris.git
cd polaris
npm install
npm --prefix command-center install
# npm install also turned on the pre-push hook (fast tests and build, see Gates below)
npm run mockup                        # the dashboard on a scratch database with demo data
```

Never run experiments against `command-center/data/`. Set `CC_DB` to a temp file, and `CC_BACKUP_DIR` and `CC_SECRETS_DIR` to scratch folders, because the daemon's backup job writes a copy at start.

## Code style

### TypeScript (`command-center/`)

- Node runs the source directly, so use erasable syntax only: no enums, namespaces, or constructor parameter properties.
- Relative imports end in `.ts`, and type-only imports use `import type`.
- All persistence goes through `Store` in `src/core`; never write SQL elsewhere. Schema changes are new append-only migrations in `schema.ts`.
- `src/invariants.test.ts` holds the safety rules as tests. If your change makes one fail, the change is wrong; do not edit the test to pass. Open an issue instead and say which rule you ran into. A new third-party source is added to `EXTERNAL_SOURCE_TYPES` in `src/core/types.ts`.

### React (`src/`)

- Every interactive control needs a 44px click target, a visible focus ring, and a keyboard path.
- Esc closes panels, drawers, menus, and dialogs. No drag-only interactions: anything a drag does, a menu or button does too.
- No hover-only actions: icon buttons are visible at rest and only brighten on hover.
- No emoji anywhere, not only in UI chrome: that covers docs, config, CLI output, commit messages, and generated files. Use lucide-react icons with `aria-hidden="true"` next to text, and an `aria-label` on icon-only buttons. The one exception is the fixtures under `command-center/src`, which keep emoji on purpose as coverage that third-party text passes through the pipeline unchanged.
- Colors come only from the tokens in `src/index.css`; no hex or rgba literals in JSX. For lucide icons, set `style={{ color: 'var(--x)' }}` rather than `color="var(--x)"`, because CSS variables in SVG attributes are unreliable.
- Dashboard data refreshes by polling `/api/events` (`src/command-center/useEvents.js`). A new view that shows server data calls `useEventRefresh`.
- No em dashes in docs or UI text.

### Offline (`src/command-center/offline*.js`, `outbox.js`)

The dashboard has to keep working when the server cannot be reached, so a new view or control has three things to get right:

- **Read through `api.js`.** Every GET it makes is stored and replayed offline for free. If a new tab reads an endpoint no other tab reads, add that call to `useMirrorWarm.js`, or the tab will be empty offline on a device that never opened it.
- **A control that writes takes `disabled` from `useOffline()`** (`offlineStatus.js`). The exception is the six task writes that `outbox.js` queues: create, update, complete, reopen, move, and comment. Do not add a queued write of any other kind without opening an issue first: the list is closed on the server too, and `command-center/src/invariants.test.ts` says so.
- **Leave recovery on.** Navigation, filters, Refresh, Retry, and the Connection form are never disabled offline. The Backups card under that form is not recovery: everything in it that writes is off, and a passphrase is never queued.

A unit test that touches `api.js` resets the copy and the queue in `beforeEach` with `setCacheBackend(memoryBackend())`, `setOutboxBackend(memoryBackend())`, and `resetOfflineStatus()`. A UI test goes offline with `page.context().setOffline(true)`, after waiting for the service worker to cache the page (see `goOffline` in `e2e/offline.spec.js`).

## Testing

```sh
npm run test:fast        # server tests, typecheck, dashboard unit tests (the pre-push hook and CI run this)
npm run test:ui          # builds, then Playwright UI tests at 1280px, 390px, and 320px, plus light, high-contrast, and landscape
npm run test:all         # both
npm test                 # dashboard unit tests only (Vitest + jsdom)
npm run test:desktop     # the desktop shell's Rust tests (cargo test)
npm run test:desktop:ui  # builds the debug desktop app and drives its real window (desktop/e2e)
(cd mobile && npm run apk)  # builds the Android app; needs a JDK and the Android SDK, see mobile/README.md
npm run test:android     # the Android app's instrumented tests on a running emulator (mobile/README.md, Testing)
cd command-center && npm test && npm run typecheck
```

- **Server tests** use node:test and live next to the code as `*.test.ts`. A new module gets one. Use `openStore(':memory:')` or a temp folder, never `data/`, never the network, and nothing that depends on the machine: no real paths from your dev folder, and no real GitHub sign-in. Pass a token, a fake fetch, or `memorySecretStore()`.
- **Dashboard unit tests** use Vitest with jsdom and Testing Library (no jest-dom) and live next to the code as `*.test.js` or `*.test.jsx`. Vitest globals are off: import from `'vitest'` and call `cleanup()` in `afterEach`.
- **UI tests** live in `e2e/`. Every worker starts its own server on its own scratch database (`e2e/server.js`, through the fixture in `e2e/fixtures.js`), so tests run four at a time and share nothing. Import `test` and `expect` from `e2e/fixtures.js`, never from `@playwright/test`: the fixture freezes the browser clock to the moment the database was seeded, so due dates read the same on every run. Tag every `test.describe` with `@flow`, `@a11y`, or `@theme` (`@landscape`, `@narrow`, `@perf`, and `@visual` move a test to one of the extra projects in `playwright.config.js` and out of the desktop and phone runs; `@all-widths` runs it at 320px and in landscape as well as at desktop and phone); `e2e/conventions.test.js`, run by `npm test`, fails on a missing tag, the wrong import, or a class selector. Select by accessible name (`getByRole`), never by CSS class. A test that changes data creates its own task with `createTask` from `e2e/support.js`, and never asserts an exact count on the shared seeded project. Open a task panel with `openTask`, since the middle of a desktop row is an inline cell menu.
- **App-only code** (src/command-center/nativeApp.js, shareIntake.js, reminders.js and the Reminders card) is tested with Vitest; a test that needs the bridge installs a fake `window.Capacitor` (see `nativeApp.test.js`) and removes it afterwards. The shot states for the Android app (`e2e/shots.spec.js`) install a stand-in bridge with `page.addInitScript`. The Android project itself (`mobile/android`) has instrumented tests in `mobile/android/app/src/androidTest`, run on an emulator with `npm run test:android` (see mobile/README.md, Testing): run them, and build the APK, when `mobile/` changes.
- **Layout checks.** `e2e/clipping.spec.js` fails on anything cut off, a focus ring included, at every width the projects cover, and `src/layout.test.js` on the source patterns that cause it (see "Nothing is cut off"); `expectNoHorizontalOverflow` and `smallTargets` in `e2e/support.js` hold the page to no sideways scroll and 44px targets.
- **Accessibility checks.** `e2e/axe.spec.js` runs axe-core over every view and open panel. A violation judged wrong or accepted goes in `e2e/axe-allow.json` with a reason, and an entry that matches nothing fails the run.
- **Browsers.** The UI tests run on installed Microsoft Edge. Set `CC_UI_BROWSER=chromium` to use Playwright's Chromium where Edge is missing (Linux), and `CC_UI_PORT` to move the block of worker ports off 8791 so two clones can run at once.
- **The desktop tests** need stable Rust with the MSVC toolchain (rustup plus the Visual Studio Build Tools C++ workload). They run on a fresh checkout: the test command leaves the staged node.exe and resources out of the config, so `prepare` is not needed.
- **The desktop UI tests** (`desktop/e2e`, `npm run test:desktop:ui`) run the real debug app, Windows only. The runner stages the server bundle (`prepare`), builds with `tauri build --debug --no-bundle` (no installer, no signing), then Playwright starts the exe with `--remote-debugging-port=0` set through `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS`, reads the port Chromium chose from the profile's `DevToolsActivePort` file, and attaches with `chromium.connectOverCDP`. Run them from a normal shell: an elevated WebView2 host ignores that variable (runtime 150 and later), so the CI job, which is elevated, asks for the port through the HKLM policy `Software\Policies\Microsoft\Edge\WebView2\AdditionalBrowserArguments` instead, and `launchApp` refuses to start elevated without it. Every launch gets its own temp folder for `CC_DB`, `CC_SECRETS_DIR`, `CC_BACKUP_DIR`, `APPDATA`, and `LOCALAPPDATA` (WebView2's profile), and its own `CC_PORT`, never 8788, so the owner's real daemon and database are untouched; inherited `CC_*` variables are dropped, and only processes the tests started are ever killed. The app allows one copy per user, so close Polaris before running. They cover the cold start through the `#cc-url` handoff, reuse of a daemon that proves its token at `/api/identity`, refusal of an impostor, and the daemon stopping when the window closes. They live outside `e2e/` because that suite's fixtures (frozen clock, one server per worker, phone projects) do not fit a native window; the rules that do (role selectors, tagged describes, no exact counts) are kept. `--skip-build` reuses the last debug exe; arguments after `--` go to Playwright.
- **CI** (`.github/workflows/test.yml`) runs the fast layers on every push and pull request, and the UI tests and the vulnerability scan on pull requests into `main`; `desktop-ui.yml` runs the desktop UI tests on pull requests that touch the desktop shell, and `android.yml` runs the Android app's instrumented tests on pull requests that touch `mobile/`, `src/`, or `public/`. `weekly.yml` runs every UI project and the screenshot gallery against last week's baseline on Mondays.

Never push with `--no-verify` to get around a failing test.

## Gates

Every check that can stop a change, what triggers it, and what to do when it fails.

| Gate | Runs | When it fails |
| --- | --- | --- |
| Pre-push hook (`.githooks/pre-push`) | Before each `git push`: `npm run test:fast`, then `npm run build`, the same as the CI fast job. `npm install` turns it on. | Read the tail it prints (full log in `.git/pre-push.log`), fix the cause, push again. Never `--no-verify`. |
| `Tests` (`test.yml`) | Every pull request into `main`. One required check that needs every job below, the fast checks and the vulnerability scan included, and fails if any of them did not succeed. The one job it accepts as skipped is the path-gated UI tests (`ui`), and only when `changes` says nothing they test was touched. | Open the job that is red in the run. A skip that `changes` did not call for fails it. |
| `Reviewed` (`review-gate.yml`) | Every pull request into `main`, again on each push and each review. A commit status, not a check, set on the head commit: success when a review with a summary was submitted on it and the newest one does not request changes. A reply to an inline comment does not count. A push leaves the new commit with no status until it is reviewed. | Get the pull request reviewed on its latest commit; after a push, review again. The workflow's own job, `Set the Reviewed status`, succeeds whatever it decides and fails only when it cannot read the reviews or write the status; then re-run it. Re-run a run that shows as cancelled too: a newer push or review cancels one still going, and its check stays on the commit. Branch protection requires both the status and that job's check, so a failed write cannot leave an earlier success in place. |
| Server tests, typecheck, dashboard unit tests, build | Every push and every pull request (a push to a branch with an open pull request runs it twice, so that `Tests` can require it). | Same as the hook: reproduce with `npm run test:fast` and `npm run build`. |
| UI tests in Edge, 12 parts | Pull requests into `main` that touch anything but docs, the desktop and Android shells, and a few CI files (the `ui` filter in test.yml). | Download the `playwright-output-N` artifact (traces and screenshots), or run `npm run test:ui`. |
| Server test coverage floor | Every push and pull request. `npm --prefix command-center run test:coverage` fails under the line, branch, or function floor in `command-center/package.json`. | Add tests for the code you changed. Raise the floors when coverage rises; never lower them to get green. |
| New vulnerabilities in this pull request (`osv` job in `test.yml`, steps in `osv-diff.yml`) | Pull requests into `main`: OSV-Scanner on the merge base and on the head, failing only on an advisory the pull request introduces. The result files are kept outside the checkout, so nothing in the tree can alter the comparison. | Update the package named in the log (Dependabot opens most of these). If there is no fix or it does not apply, say why in the pull request. |
| Vulnerability gate self-test (`osv-selftest.yml`) | Mondays, on demand, and on pull requests that change `osv-diff.yml` or itself: runs the gate's steps on a head with a planted lodash advisory and symlinks over the result file names, and must see the gate fail; then on a head with nothing new, and must see it pass. Not part of `Tests`. | The gate would let a new advisory through: do not merge the change to `osv-diff.yml` until it passes. If the advisory was withdrawn, pick another package with a permanent advisory and update `FIXTURE_ADVISORY`. |
| Vulnerabilities (`osv.yml`) | Mondays and on demand: a full scan that reports every known advisory without failing, until the findings that were in `main` when the gate was added are cleared. | Not a pull request check. Update the package named in the log. |
| Property tests (`command-center/src/**/*.property.test.ts`) | In the normal suite with a fixed seed. `nightly-properties.yml` runs them every night with a random seed and many more runs. | Fix the bug, then add the shrunk input from the log as a named regression test next to the code. Do not loosen the property. Replay with `CC_PROPERTY_SEED` and `CC_PROPERTY_PATH`. |
| Desktop UI tests (`desktop-ui.yml`) | Pull requests into `main` that touch `desktop/`, `scripts/desktop.mjs`, the identity route, or the workflow: builds the debug app on Windows and drives its real window (`desktop/e2e`). Not part of `Tests`. | Open the failed run. A launch that never opened its debugging port carries the app's log, output, and child processes in the error; a later failure attaches `desktop.log`, `daemon.log`, a screenshot, and a trace. |
| Android app tests (`android.yml`) | Pull requests into `main` that touch `mobile/`, `src/`, `public/`, or the root `package.json` or lockfile: the instrumented tests (`npm run test:android`) on an emulator. Not part of `Tests`. | Download the `android-test-reports` artifact, or reproduce on an emulator as mobile/README.md describes. |
| Weekly UI matrix (`weekly.yml`) | Mondays: every UI project, screenshots against last week's baseline, report-only timings. | Not a pull request check. Read the gallery artifact and fix what regressed. |
| Dependabot (`dependabot.yml`) | Weekly pull requests for npm, cargo, and GitHub Actions, minor and patch bumps grouped. | Review and merge like any pull request. There is no auto-merge. Gradle is left out because Capacitor pins the Android versions. |
| CodeQL (`codeql.yml`) | Every push and pull request into `main`, and Wednesdays: GitHub code scanning over the JavaScript and TypeScript, the SAST step the OpenSSF Scorecard looks for. The Java and Rust shells are not scanned, since they need their own builds. | Open the alert under Security, Code scanning. Fix the code, or dismiss the alert there with a reason if it is wrong; the workflow itself fails only when the analysis could not run. |

Branch protection on `main` requires `Tests`, the `Reviewed` status, and the `Set the Reviewed status` check, and applies to admins too. `Tests` covers the fast checks, the coverage floor, the UI tests, and the pull request vulnerability scan; `Reviewed` and its job cover the review on the latest commit.

## Visual system (`src/index.css`)

The dashboard is built from layers with crisp edges, so surfaces never blend together. The table below names each layer; the values differ per theme, the meanings do not.

| Layer | Token | Used for |
|-------|-------|----------|
| Recessed | `--bg-inset` | Inputs, progress tracks |
| Page | `--bg` | Page background |
| Raised | `--bg2` | Sheets, cards, list panels, top bar (`.surface`, `.card`) |
| Higher | `--bg3` | Task panel, menus, the Inbox column header |
| Hover | `--bg-hover` | Hover on any row or item |

- **Contrast.** `--t1`, `--t2`, and `--t3` reach at least 4.5:1 on every layer (t1 and t2 reach 7:1 on the page), and `--bd-strong` reaches 3:1 for control edges. `--bd` is for dividers only. Measure any new color against every layer it can sit on before using it.
- **Depth.** Raised surfaces use `--shadow-1` (a lit top edge, a 1px dark ring, and a 1px drop: a resting panel sits on the page rather than floating over it); floating ones use `--shadow-pop`; recessed ones use `--shadow-inset`. Avoid soft glows and translucent blur.
- **Buttons.** `.btn` (raised, outlined), `.btn-primary`, `.btn-success` for positive confirms such as Accept, `.btn-danger`, `.btn-ghost`, and `.icon-btn` (44px square, add `is-danger` for delete). One filled button per toolbar (the main action); the rest are `.toolbar-btn`, quiet text buttons that take `is-active` while their setting is in effect. On My tasks an applied Filter, Sort, or Group names its value on the button ("Filter: 2", "Sort: Name") inside a `.toolbar-chip` with an X that clears it, and its popover (`.view-pop`) has the title with Clear or Reset at the right, short choices as `.sheet-chip`s, and long ones as rows that open to their lists. Menu items styled inline use `.hover-surface` for hover feedback.
- **Lists.** The task list is a flat table on the page, not a card (`.mytasks-list`): a hairline (`--bd`) under each row and between the columns from the third on, `--bg-hover` on hover, no striping, a flat column header stuck above it, and a 44px header row per group (`.mytasks-section-header`: title, count) with a 16px gap before each group after the first. The open row uses `--bg-selected` with a 3px blue left bar. A task with open subtasks shows their count after its name (`.subtask-chip` in a 44px `.subtask-toggle`), which shows them under it as indented rows (`TaskTree` in TaskRow.jsx); the inline new row (`.inline-add-row`) opens at the top of its group with an empty check circle where a row has its check. `.is-striped` (`--bg-zebra`) remains for the Inbox table. Put `.flush-last` on a row container inside a bordered panel (`.surface`) to drop the divider under its last row where it would double the panel's edge; never on a flat list such as My tasks, where the last row's column lines would end with no line under them.
- **Board.** A lane is a header band (`.board-lane-head`, on `--bg2`: the section name in bold and the count in `--t3`) over cards (`.board-card`) that sit straight on the page; there is no lane box. A card is the list's check circle (`.task-check`, which completes it), the card face that opens the task (the title, the priority pill, and a foot with the assignee's `Avatar` and the due date in the list's words and colours from `formatDueCell`), and the Move arrow, each a 44px target with its ring drawn inside. Each lane has Add task (`.board-add-task`) under its last open card, or at its top when it has none, which opens a blank card that creates a task in that lane's section. There is no Add section: the API has no way to make a section on its own.
- **Projects and people.** A project is always shown with its colour: `colorFor(name)` in shared.jsx picks one of the accent tokens by the name, and `ProjectChip` (a dot and the name on a pill) or `ProjectAvatar` (a 28px tile with the initial) draws it. An assignee gets `Avatar` (initials in a circle, same colour rule) next to the name in the panel, in the list's Assignee column (off by default, in the Columns menu), and on a board card. Nothing is stored.
- **Due dates.** One picker everywhere: `DueDateMenu` (a dialog that opens on the month, `MonthCalendar`, with focus on the task's day: the quick dates Today, Tomorrow, Next Monday, and No date as `.sheet-chip`s, then Add time, which opens a time box with Remove time; a day or a quick date saves and closes at once, and a Repeat button under the month, off by default like Add time, that opens Repeats (`RepeatPicker`, with the next dates tinted through `MonthCalendar`'s `marks`) on Does not repeat and saves each choice at once, with Remove repeat to turn it off; a task that repeats opens with it on; `.due-pop` in index.css) behind the list's Due date cell and the panel's Due date field (`.due-field`: a calendar circle, dashed until set and green once set, then the date as the list writes it). Priority is a `.priority-pill` in lists and cards and a `.priority-select` pill in the panel. A repeating task shows a `.repeat-glyph` after its date in rows and on cards, and the panel's Repeat menu beside the due date offers the quick picks worded from the due date (`quickPicks` in recurrenceRules.js: Does not repeat, Daily, Weekly on Wednesday, and so on) and Custom, which opens the builder (RepeatBuilder.jsx) in the panel under the due date, or the Recurrence box under More details for a rule the builder cannot show; `repeatLabel` in dueDates.js words the current rule. A new task's date is picked in `AddDuePanel` instead (InlineTaskInput.jsx on a desktop, the New task sheet's date step on a phone), laid out as Asana's: the month (`MonthCalendar`), the quick dates, and `RepeatPicker` (RepeatBuilder.jsx, the Repeats choice over the builder's `compact` form), with the repeat's next dates tinted on the month (`.cal-day[data-repeat]`, `--blue-soft`) and a footer (`.add-due-foot`) that sticks to the bottom of the popover or sheet. A pick there only selects; the footer's button submits.
- **Navigation.** `.nav-item` rows carry the view's icon (set on the item in App.jsx) and sit on a rounded pill inset from the column's edges; the open view is `--bg-selected` with a blue icon. The sidebar also lists the eight busiest open projects under a `.nav-group-label`, each with a `.nav-project-mark` square in its colour; choosing one opens the Board on it (`onSelectProject` in Sidebar.jsx, `projectId` on BoardTab).
- **Tints.** Chips and banners use the `--*-soft` tokens with the matching solid color for text.
- **Motion.** Transitions are short (0.15s or less) on background, color, border, and shadow only, apart from the width of a `.progress-fill`. The one animation is the completion celebration (`CompleteBurst.jsx`, `.check-pop`, `.complete-burst`, and `.mytasks-row.is-completing` in index.css): the check pops, a ring of dots in the accent tokens bursts out of it and stays inside its 44px target, and a completed My tasks row or Board card (`.board-card.is-completing`) flashes green and fades for 700ms (`COMPLETE_EXIT_MS`) before the refetch drops it. A row's check circle is empty at rest and shows its tick on hover and once done. `prefers-reduced-motion` turns all of it off, and a completed row then leaves at once.

**Light and dark.** Two themes: the dark one on `:root` and the light one in the `:root[data-theme='light']` block right after it. Those two blocks are the only place a color is named, so a component rule is written once and a new token has to be given a value in both. The light theme flips the depth model (recessed is darker than the page, raised goes toward white, hover darkens rather than lightens) and re-picks every accent rather than lightening it, since a pale accent that works on `#17191e` has no contrast left on white. Its tints are opaque, mixed into `--bg2`, so the accent text on a chip measures the same wherever the chip sits.

`src/theme.js` owns the choice (System, Light, or Dark; `useTheme` in `App.jsx`, the menu behind the top bar's Theme button) and writes the resolved theme to `data-theme` on `<html>`. System follows `prefers-color-scheme` and keeps following it while the tab is open. A copy of that resolution runs as a pre-paint script in `index.html` so a reload never flashes the wrong theme; if the storage key or the fallback changes in one, change it in the other. `npm run shots` takes every screenshot in both themes (it emulates the OS setting, which is what the default System choice follows), so a change is seen on light and dark without any extra step.

## Responsive

One breakpoint for the whole dashboard: phone is `max-width: 640px`. Static layout differences live in `src/index.css` under a media query on class names; layout computed in JavaScript (the My tasks grid template) uses `useNarrowBreakpoints` in `src/command-center/columnsState.js`, which exposes `phone` alongside the older 900 and 600 flags. No Tailwind breakpoint classes.

Above 640px the navigation is the sidebar in `src/Sidebar.jsx`, which lists every view and leaves the top bar without a menu button. Under 640px it is the tab bar in `src/BottomNav.jsx` (More opens the drawer), new tasks come from `src/command-center/NewTaskSheet.jsx` behind the floating New task button, and the dashboard installs from `public/manifest.webmanifest` (icons by `node scripts/icons.mjs`). Layout work is verified with screenshots, and they are one command.

## Nothing is cut off

Every word and every control is seen in full: at every width from 320px up, between the breakpoint and the desktop width, on a phone turned sideways, with the task panel open, and with long text in it. A tester or a screenshot at 1280px will not show most of these, so the rules below are checked by a test (see the end of this section).

- **Our words wrap; they are never shortened.** Labels, headings, buttons, menu items, column headers, banners, and empty states wrap onto another line or the layout changes to make room. Never `white-space: nowrap` with `overflow: hidden` on text we wrote.
- **User text may be shortened only in a dense row or card**, with an ellipsis or a line clamp, and only when the whole text is one step away: on the element's `title` or in an accessible name around it (the row's "Open ..." button, for example), and in full in the panel the row opens. `ProjectChip` sets its `title` for this.
- **Long words break.** Any box that shows user or server text (titles, notes, digests, URLs, ids, repo names) sets `overflow-wrap: anywhere` or `break-word`, so a URL wraps instead of pushing the page sideways. A code block keeps its lines and scrolls in its own box (`overflow-x: auto`).
- **`overflow: hidden` is for rounded corners and ellipses**, not for hiding what does not fit. A box that can hold more than it shows scrolls (`overflow: auto`), and all of its content is reachable: never centre content in a scroll box with `justify-content: center` or `align-items: center` (what overflows the start can never be scrolled to); use `safe center` or auto margins.
- **Flex and grid children that hold text get `min-width: 0`** so they can shrink, and a row of controls that can outgrow its line wraps (`flex-wrap: wrap`) or moves the extras into a menu. Nothing is pushed off the side.
- **The page never scrolls sideways, and that is never hidden** with `overflow-x: hidden` on `html`, `body`, or the app shell, which turns a scrollbar into content nobody can reach.
- **A table with more columns than a phone holds becomes cards on a phone**, each cell on its own line and each control beside its label (the GitHub repos in `.repo-table`, the Inbox list). The card has no column header, so a plain text cell keeps its label in the accessibility tree (the repo's project name reads "Project Octavium"); only a control that names itself (a switch) hides its label with `aria-hidden`. A sideways-scrolling table is a last resort, never for controls: a switch past the edge is one nobody finds.
- **A title field grows with its text.** The task panel's title and assignee and the New task sheet's name are textareas sized by `useFitToText` (src/command-center/useFitToText.js), so a long title is read whole; Enter still saves. The hook returns the ref to put on the box and follows the box itself, not a ref object: a panel that reloads mounts new boxes, and one with the same text as the last (a subtask with its parent's assignee) is measured all the same.
- **Fixed and sticky layers never cover content for good.** The top bar, the column header, the bottom tab bar, the floating New task button, and sheets leave room: the scroll area under them has padding at least their height, so the last row scrolls clear of them. The page's `scroll-padding` does the same for whatever is scrolled into view, a control reached with Tab included.
- **Focus rings and highlights show whole.** An outward ring reaches 4px past its control, where a box that clips, a sticky bar, or the next row's highlight paints over it. So a control that touches its neighbours or an edge (a row, a cell, a sidebar item, anything in a menu) draws its ring inside: add its selector to the `outline-offset: -2px` rule in `src/index.css`. Content in such a row stays 4px clear of the row's edge, and a scroll box that holds focusable cards keeps 4px of padding round them for their rings.
- **Lines close.** A row that draws column lines has a line under it: its own divider, the next row's, or the border of the panel it ends on. `.flush-last` drops the last divider only inside a bordered panel (`.surface`).
- **Menus and popovers fit the screen.** Use `Popover` or `Menu` (src/command-center/Menu.jsx), which keep inside the viewport, cap the height to the room there is, and scroll.

**The checks.** Three helpers in `e2e/support.js` measure the page in the browser and return one line per problem. `clippedContent` finds text a box hides (an ellipsis is excused only outside a panel or dialog, and only when the full text is in a `title` or accessible name around it), text or a control off the side of the screen or out of a scroll box's reach, a control in a fixed layer that runs off the screen, and a control that, scrolled to the middle of the screen as far as it goes, is still cut off or has something drawn over it. `hiddenFocusRings` focuses each control as from the keyboard and compares photos with and without its ring, side by side, so a ring that is clipped, painted over, or off the screen is caught whatever the cause. `danglingLines` finds rows whose column lines end with no line under them. With a menu, popover, or modal open they check only that layer.

`e2e/clipping.spec.js` runs all three on every view and the main panels, sheets, and menus in the desktop, phone, 320px, and landscape projects (the `@all-widths` tag), and on every view at 641, 800, and 1024px. Its last test plants each kind of problem on a page of its own and fails if a check stops seeing one, and `e2e/conventions.test.js` lists the suite as Playwright selects it per project and fails if a view, the task panel, or the long-name cases are left out at any of the four sizes, since a tag that moves a group to an extra project also drops it from the desktop and phone runs. `npm run shots` runs the first and the last on every shot and lists what they found under "Cut off" at the end of the run. `src/layout.test.js`, run by `npm test`, catches the usual causes in the source before a browser starts: nowrap text clipped without an ellipsis, `overflow-x: hidden` on the page shell, a centred scroll box, an inside-ring selector dropped from the rule, a New task button with no room under it, and `.flush-last` on a flat list.

A new view, panel, sheet, or menu adds a test to `e2e/clipping.spec.js` next to its state in `e2e/shots.spec.js`. There is no allow list: fix the layout. If the check is wrong, fix the check and add the case to its self-test.

## Screenshots

`npm run shots` builds the dashboard, starts the same scratch server the UI tests use, and photographs every view and its main states (the task panel, the task panel with a thread, the new task sheet, the due date and sort menus, the drawer, the inbox accept form) at 390 and 1280px in both themes: about 300 shots in about three minutes. The states are the tests in `e2e/shots.spec.js`; add one there when a new view, panel, sheet, or menu appears.

Files go under `.shots/` (ignored by git): `current/` for this run, `baseline/` for the last accepted look, `diff/` for the changed pixels, and `index.html`, a gallery with changed shots first. The run ends with a list of what changed since the baseline. Read each of those, at both widths and in both themes, fix what is wrong, and then `npm run shots -- --accept` to make the current shots the baseline. `--only mytasks,inbox` limits the run to some views and `--no-build` reuses the last build.

Baselines stay on the machine that made them, since text rendering differs from one machine to another. Text that changes from run to run without meaning anything is dealt with in the spec, in the smallest way that keeps the rest visible: the scratch backup folder's name and time on the Settings page are masked, and the digest's task and goal ids are rewritten to fixed placeholders on their way to the page, so a change to how the digest looks is still reported. A mask never covers a whole card, since everything under it would change unseen. Absolute dates, such as an overdue task's, change from one day to the next, so a shot that only differs in a date is accepted as is. `--window-size` cannot produce a phone width in headless Edge (it floors at about 504 CSS px); Playwright's viewport emulation has no such floor.

The run also lists every shot in which something is cut off (see "Nothing is cut off" above); fix those before accepting.

Every change to how the dashboard looks or lays out ends with this run, and the pull request names the shots that were checked under "Screenshots checked" in the template.

## Pull requests

1. Branch from `main` and keep the change focused: one feature or fix per pull request.
2. Run `npm run test:fast` always, `npm run test:ui` when the dashboard changed, and `npm run test:desktop` when `desktop/` changed.
3. New behavior has a test. A dashboard control has a UI test that finds it by its accessible name.
4. Use conventional commits: `feat:`, `fix:`, `docs:`, `refactor:`, `chore:`. No co-author or generated-by trailers.
5. Fill in the template (`.github/pull_request_template.md`): what changed, which shots were checked, which tests ran.

Markdown in this repo uses ATX headers, tables for structured data, and fenced code blocks with language hints. Text files use LF line endings on every platform, set by `.gitattributes`.
